# 推荐系统架构（18）：推荐系统十年的工程演进

## 1. 开篇

我从最开始 2013 年左右开始做推荐系统，陆陆续续做了近十年。之后工作重心转变，但还会持续关注推荐系统方面技术的发展。回顾这十几年，最容易让人记住的是算法，从 LR 到 GBDT，再到深度学习模型，再到近年来热门的大模型，各自在表达能力、计算成本和迭代效率上有不同的取舍。不过真要看工业化推荐系统，都是实现时候的选型和细节。当用户量涨上来、内容多起来、业务需求变复杂、迭代节奏变快的时候，就要看整个系统里，哪个环节首先撑不住了。然后为了适应当时的诉求，系统做了哪些看起来“跟算法无关”的改动。

这是推荐系统架构系列的收官篇。前面逐篇拆过特征、画像、召回、精排、重排、实验和 Feeder。这一篇我们会把整个系统串起来，讲讲在线服务哪些模块会出现、为什么拆分又为什么合并；离线最早几个人用 SQL 脚本就能跑起来，后来为什么会有平台。我在文章里面讲的不是标准答案，只是之前真实走过的路径。通过这个过程，你可能看到业务规模、时效要求、模型能力、团队协作等方式的变化，驱动系统也在跟着变化。

前半篇讲的是我实际走过的路，不是行业统一的升级顺序。最后会从亲历的终点往前看，聊聊后来关注的几个技术方向。

## 2. 演进地图：五条线在变，节奏并不同步

在展开之前，我们先来看一张地图。推荐系统的演进，我把它分成下面五条线，它们同时在变化。

- 算法：从 LR 到 GBDT，再到 DNN。序列建模和多目标预估放在第 8 节讨论。
- 召回：最开始只有倒排和热门，然后逐步增加 CF、探索、再加向量。
- 在线架构：开始把多处逻辑都放在引擎服务中，后来逐步拆分出 Traffic Splitter、Prediction Server 等独立服务。User Profile 开始是独立服务，描述用户，后来随着模型升级，用户画像也作为用户特征合并到 Feature Server 中。
- 离线体系：从开始的分散任务，到平台化，再到数据仓库。
- 特征和用户兴趣：开始用分类和关键词描述用户兴趣，后来有更丰富的标签、统一表示，再后来增加 Embedding、长短兴趣。

这五条线不是同步推进的，因为都是团队在当时遇到瓶颈的情况下，一块一块的补。有些变化也依赖其他环节先做好准备。例如，向量召回需要先具备向量生产和索引更新能力，反馈时效提升也会推动数据处理链路调整。

回头来看之前的系统，我们一般不会用最新架构的标准去说那时候系统太过“简陋”，那是它在当时条件和约束下给出的最好答案。我们看一套系统的演进，重点看两个：第一是每个阶段它在当时解决了什么样的问题；第二是为了解决这个问题，系统放弃了什么、引入什么新的成本。

关于这个路线演进，我给不出一个确切的编年表，因为演进都是渐进、重叠的。下面我们分阶段讲讲这几条的发展。

## 3. 算法演进：从 LR 到 GBDT 再到 DNN

算法的演进，之前在第 2 篇已经详细介绍过，这篇文章里就不再重复详细的演进历史。这里概述一下，每个模型的迭代，怎么驱动整个工程升级的。

早期推荐用的 LR 模型，特点是简单、解释性强，训练起来很快。不过 LR 的表达能力有限，需要人工来对特征进行交叉组合。所以这个阶段团队要做很大量的特征工程，实验哪些特征放在一起有用。这个时候的模型本身比较简单，主要工作在特征工程。

后来换成 GBDT，树可以沿着不同特征逐层分裂，学到一些原本需要人工枚举的组合。在我们当时的系统里，效果有了提升，线上打分也比 LR 更耗计算。那时流量也在增长，我们在 GBDT 上线后不久把 Prediction Server 拆了出来，让打分服务可以单独扩容。这次拆分的细节放在第 5 节。

再到 DNN，网络可以学习更复杂的特征组合，减少一部分手工交叉的工作。工程上的变化更多落在样本构建、特征输入和模型部署上。已有的 Prediction Server 让我们可以独立调整模型发布节奏和推理资源；具体用什么机器，要看模型、流量和延迟预算。

算法模型从简单到复杂，在工程实现上，不仅仅是把模型训练代码换掉，然后线上模型推理改个引擎这么简单。实际上，换一个能力更强的模型，牵动的是整个系统多个服务。特征需要重新计算、在线推理服务和配套的特征工程需要建立、离线样本重新生成、模型重新训练等等。因此，更换模型时，模型本身可能只是整个改动的一部分，围绕模型的工程配套，才是工程化真正耗时的部分，也是系统变更的大头。

## 4. 召回演进：召回源的增加

在我经历的系统里，排序模型先后换过几次，召回则主要靠增加不同来源的候选，补足已有召回的覆盖。

最开始时，系统只有倒排召回和热门召回。倒排召回是指根据内容的分类、关键词这些标签属性建立倒排，用类似搜索那种倒排的方式把相关内容召回出来。然后再用热门召回补充热点内容，也作为新用户做兜底。这个阶段是推荐系统的初始阶段，首先要解决能不能把内容按个性化需求推荐出来。

后来我们增加了协同过滤（CF）和探索。CF 利用相似内容或相似用户的行为，补上标签匹配覆盖不到的关联。比如一个用户还没看过某类内容，但和他行为相似的用户经常看，CF 就有机会把这类内容召回。它能拓宽候选来源，但也可能偏向热门内容。

探索有两个作用：一是给用户一些还没接触过的兴趣方向，帮助拓展兴趣；二是给反馈还不够的新内容或冷启动内容分配一定的曝光机会，帮助系统尽早判断用户是否愿意看。探索会占用一部分曝光，配额过高时可能影响短期点击率，因此需要控制占比，并观察后续反馈。

最后增加的召回源是向量。向量召回把用户与内容映射到可比较的表示空间，能够补充精确标签匹配覆盖不到的候选。这个空间表达的是行为关联、内容语义，还是两者的结合，取决于模型的输入与训练方式。

双塔模型（Two-Tower）是向量召回的一种典型做法。用户塔根据用户特征和画像输出用户向量，内容塔根据内容特征输出内容向量。训练时用选定的正、负样本学习两者的匹配程度；没有发生交互的内容可能根本没曝光过，不能直接视为不相关。内容向量可以通过第 17 篇介绍的 Feeder 写入在线检索索引，召回时再用用户向量查询。

回看这几次变化，CF 补的是行为关联，探索补的是兴趣拓展和反馈不足时的曝光机会，向量补的是表示空间里相近的候选。增加一路以后，还要处理候选配额、去重和融合，并验证这一路是否真的带来了新增覆盖。多路召回的工程细节可参考第 13 篇。

## 5. 在线架构演进：拆分和合并

在线架构的演进，既有拆分，也有合并，它的设计要根据当时的业务状态和团队情况来确定。

最开始做推荐系统时，主要的业务逻辑都集中在一个单体服务中。这个服务包含了如今的 Traffic Splitter、Engine、召回调用、打分排序（LR 模型）、重排等大部分逻辑。外部服务有独立的 User Profile 保存用户画像，以及召回源，主要是前面说的倒排召回和热门召回（保存在 Redis 中）。因为在当时，为了把业务快速上线，后端的开发也都在一个团队，所以就在一个服务中快速把整个流程实现。这样的设计会导致一些逻辑边界划分的不是很清晰，例如要上一个新模型，除了改特征计算、模型推理等部分，可能还会影响分流部分的逻辑。

接下来进行了第一次拆分，把 Traffic Splitter 独立。这次拆分是因为 Traffic Splitter 主要负责流量治理，它和推荐计算的核心业务边界相对比较清晰。拆分后，Traffic Splitter 负责实验分流、灰度路由和入口降级等流量治理工作，也可以和推荐引擎分别扩缩容。Traffic Splitter 独立之后，参数调优类的实验迭代频率可以更高，可以在线上更快速尝试各种参数组合，最后选取最合适的那组。

第二次拆分是把精排打分拆分为独立的 Prediction Server 服务。在 GBDT 模型上线之后不久，精排打分推理所需要的计算资源变得比 LR 模型更高。同时期流量也在扩大，要求打分服务扩容来支持。而没拆分之前，Engine 和 Prediction 在一个服务中，要扩容只能一起部署，管理起来相对比较复杂。所以这个阶段决定把 Prediction Server 拆分成独立服务，它可以采用不同的硬件选型（计算优化型机器）、有不同的资源扩容缩容策略，也可以有不同的发布节奏。独立的 Prediction Server 对模型的管理也更规范，同时上线更多模型变得更容易，模型迭代频率也变得更高。

下一轮的架构重构是引入独立 Feature Server。在引入 Feature Server 之前，特征是保存在裸 Redis 中，以 U_XXX（用户特征）、D_XXX（内容特征）、C_XXX（部分交叉特征）的 Key 形式存放。以裸 Redis 方式管理，特征的版本、Key 定义，调用端（Engine、Prediction Server）和 Feeder 都需要知道。修改 Key 定义、或者版本变更，相关的几个服务都要跟着一起改，耦合严重。所以决定封装独立的 Feature Server 服务，把特征怎么存储、版本管理、Feature 读写、内部双版本切换批量更新等逻辑都封装到服务中，外部只需要调用对应接口即可。

后面还有一次变更，是把 User Profile 合并进 Feature Server。随着模型的升级，User Profile 服务保存的画像，已经全部变成用户特征的一部分，这些特征在 Feature Server 中都有保存。因此独立的 User Profile 存在意义不是很大，把相关内容全部放进 Feature Server，可以节省一个独立服务，Feeder Pipeline 也可以节省一个目标，还减少了 User Profile 和 Feature Server 之间可能存在的不一致。所以架构的演进不仅只有拆分，也会有合并。

作为离线系统和在线服务之间的桥梁，Feeder 本身的演进，已经在上一篇文章中描述过，此处不再重复。

通过这些架构的演进过程，我们可以看到，每一个架构的选型，都是和当时的实际业务情况，以及团队情况密切相关。初期时，为了快速开发、快速上线，可以容忍一些服务之间的耦合存在。后面随着业务的发展、流量的上涨、团队的拆分等，在线系统也要随之变更以适应。“服务拆没拆”并不代表这个架构是不是先进，拆分和合并都是架构演进的手段，服务的边界跟着真实的需求走。

## 6. 离线体系演进：从分散任务到数据仓库

离线系统负责数据的生产，也经历了三个阶段。这三个阶段之间不是简单的替代关系：天级批处理一直保留，后来又增加了按 5 分钟一批运行的近实时（NRT）Pipeline。这里的 5 分钟是批处理周期，产物何时在线可用，还取决于计算、分发和加载。

第一阶段：分散任务。这个阶段内容保存在 Content Pool 中，以 HBase 作为存储实现。用户的反馈按天保存在 HDFS 上。各类的 Pipeline 包括有：内容 Pipeline、用户画像 Pipeline、天级反馈统计 Pipeline 等，都是分散在多个机器上，以各自的方式（例如 crontab）在运行。各 Pipeline 之间没有统一的组织，计算逻辑也是分散在多个 code repo 中。各自读文件逻辑、计算逻辑不一样，这就导致重复计算很多、计算口径不统一等问题频繁出现。一个典型的例子，“最近7天点击次数”这样的特征，有的 Pipeline 按过去 7 个自然日计算，有的按 Pipeline 运行时间相对过去 7 天来计算，导致结果不一致，特征不一致。

第二阶段：初步平台化。Content Pool 按天 dump 快照放到 HDFS，和天级的反馈数据类似目录组织。然后创建一个初步的数据平台，数据的输入是内容和反馈的 HDFS 目录，提供统一的定时任务调度。特征的计算逻辑初步规范化，把一些特征的计算抽取成公共库，各 Pipeline 引用公共库进行计算。这样的统一调度、规范化特征计算、统一的数据输入，让各类计算 Pipeline 变得有组织，让特征不一致出现的频率有了明显的下降。

第三阶段：构建数据仓库。统一调度以后，各 Pipeline 仍主要按日期目录读取文件，即使共用了计算库，也可能各自重复执行相似的加工。数仓改变的是组织与使用数据的方式：按统一口径把可复用的加工结果沉淀成共享表，供下游读取。HDFS 仍可作为底层存储。数据仓库的具体设计参考第 6 篇《用户反馈闭环》，此处概述一下引入数据仓库之后的几点收益：

- 分层建模、统一加工路径和逻辑。数据仓库采用 ODS、DWD、DWS、ADS 分层设计方式，外加 DIM 表。各层负责对应粒度的数据，层递进做成统一的路径，避免之前分散 Pipeline 时各自读文件各自计算的问题。

- 减少重复计算和口径不一致。DWS 层提前产出可复用的聚合结果，下游 Pipeline 可以按统一口径取数。

- 可追溯与历史回溯。DIM 表每天做快照、Feature Log 保留版本，这样在 Pipeline 中可以把日志、特征、快照等按规范记录，支持历史数据的回溯。

- 支持交互式分析和业务报表。ADS 层数据直接面向业务，可以给报表、看板提供定制化数据。在以前，运营如果想看数据，需要临时写脚本处理计算。

- 反馈数据规范与对账。从客户端上报到数仓入表，统一字段定义，处理版本兼容，并通过离线对账发现数据缺失或口径不一致。

从这条线看，分散任务到平台化，是从“能算”到“稳定地算”；平台化到数仓，是从“稳定地算”到“一致地、可追溯地算”。

## 7. 特征和用户兴趣演进

特征方面，主要是用户兴趣怎么表示方面，也经历过几个阶段。各阶段不是完全替代关系，而是叠加演进；线上系统往往是稀疏标签、Embedding 并存。

最开始时，内容特征主要由分类、关键词和基础属性组成。以下用虚构数据示意。一篇文章的特征可以表示为：“分类：体育”、“分类：篮球”、“关键词：2026NBA总决赛”，基础属性：发表时间、作者、首发平台等。用户兴趣基于分类和关键词统计，表示成一组“标签:权重”的键值对（本质上是一个稀疏的兴趣向量）。例如某个用户的兴趣可能是：`[CAT_篮球:0.8, CAT_足球:0.2, KW_NBA:0.77, KW_杨翰森:0.53, KW_中超:0.46]`。这个阶段兴趣区分相对粗糙，但它是真正的千人千面个性化的开始。代价是标签依赖人工定义和内容侧标注，覆盖面受限于标签体系本身，长尾内容和新兴热词容易漏掉。

下一阶段，在之前的分类和关键词之外增加更丰富的标签体系，主要包括实体和主题等。实体是内容中具体的对象，例如人物、球队等；主题是一组内容的共性归纳，例如“2026季后赛”等。用户画像的表现形式，是丰富标签之后的稀疏向量。同时用户的基础属性作为画像特征单独表示，例如年龄段、性别、地域、注册时长、活跃度等，可离散化后与兴趣标签一起拼成稀疏特征。

例如，一个用户的兴趣可能是：`[CAT_篮球:0.82, CAT_足球:0.18, KW_NBA:0.76, ENT_杨翰森:0.58, TOPIC_2026NBA总决赛:0.66]`。他的基础属性特征可表示为：`[AGE_25-30:1, GENDER_男:1, CITY_北京:1, REG_3年以上:1, ACT_高活跃:1]`。如果把基础属性和兴趣标签拼在一起，整体用户画像可以写成：`[CAT_篮球:0.82, CAT_足球:0.18, KW_NBA:0.76, ENT_杨翰森:0.58, TOPIC_2026NBA总决赛:0.66, AGE_25-30:1, GENDER_男:1, CITY_北京:1, REG_3年以上:1, ACT_高活跃:1]`。

第三阶段，在稀疏标签特征基础之上增加 Embedding 向量。内容侧可以对标题、正文、实体、主题等做语义 Embedding，用户侧可通过行为聚合、ID Embedding 或内容 Embedding 汇聚来表示兴趣。用户兴趣表示从高维稀疏向量慢慢变成了 “稀疏标签 + 低维稠密向量” 的混合形式。标签便于解释，也能在缺少行为数据时提供线索；这个阶段加入的稠密可泛化向量，能捕捉标签表示不出来的相似性。不过稠密向量的加入，会导致可解释性变差，向量维度高带来的是存储和检索开销变大。

第四阶段，区分长期兴趣和短期兴趣。之前无论是标签还是 Embedding 向量，描述的都是用户整体喜欢什么，没有区分用户是一直喜欢和最近突然喜欢。因此，此阶段引入用户的长期兴趣和短期兴趣，分别建模。长期兴趣表示用户稳定的偏好（例如多年关注的球队），短期兴趣反映近期行为带来的临时偏好（例如突然的热点事件）。当时使用方式比较简单，把两类兴趣特征拼接后交给打分模型。

## 8. 从终点向前看，几个技术方向

以上的系统演变，都是我曾经经过的推荐系统演进，每个阶段的设计都是和当时团队情况以及业务情况相关的。那之后，我在工作中没有直接参与推荐相关的系统开发，不过也一直关注着业界的发展。以我当时实际经历过的推荐系统为终点，继续向前看，摘录几个方向，和大家一起探讨。

在**用户理解**方面，首先是兴趣摘要演进到序列建模。之前的用户标签到向量再到长短期兴趣分离，都是对历史行为的压缩。序列建模是根据时间排列的内容、行为类型、时间间隔和上下文，让模型从这些原始序列中学习行为顺序，找到近期意图和兴趣变化。它比“压缩后的摘要”保留了更多信息，代价是工程要求整体上移：序列的生成、存储、时序对齐、去重截断、在线更新和缓存，以及训练与服务的序列一致性，都要重新设计；序列越长，性能和成本的平衡也越难做。

另一个方向是让模型根据当前候选提取兴趣。我们之前把长短期兴趣特征拼好，供不同候选共同使用。用 DIN 这类方法时，模型可以针对当前候选，对历史行为赋予不同的权重；DIEN 在这个基础上还显式建模兴趣随行为顺序的演化。比如在评估篮球内容时，模型可以更关注篮球相关的历史行为。在这些方案中，候选相关的计算会增加精排开销，实际使用时需要在历史长度、候选数量和请求延迟几方面权衡。

在**学习闭环**方面，我们来看两个问题：用户的反馈多久能影响推荐，以及这份反馈最终被用来优化什么。

第一，**数据更新和模型学习有各自的节奏。** 比如用户刚看完几条篮球视频，这些行为可以先进入近期序列，或者更新短期兴趣特征。即使模型参数没有变化，下一次请求也可能排出不同的结果。模型要从这批行为中学到新的规律，还需要经过曝光和反馈关联、样本构建、训练、验证与发布。即使使用 5 分钟一批的近实时 Pipeline，也要看它更新的是哪些数据，以及这些数据何时在线生效。训练也有自己的时效要求：例如转化可能在曝光很久以后才发生，不能因为暂时没收到反馈，就直接把样本当作未转化。

第二，**训练目标要和最终的推荐决策衔接起来。** 例如，精排只预测点击率，可能更容易把标题吸引人、但用户点进去很快就退出的内容排在前面。可以同时预测点击、停留和互动，再根据场景决定这些信号怎样参与排序，并通过线上实验观察收益和副作用。这个问题也会跨过单个阶段：如果召回没有留下那些点击率一般、但用户愿意看完的内容，精排就没有机会把它们选出来。一种做法是把精排对候选的评价用作召回训练的辅助信号，同时观察候选覆盖有没有变窄。召回和精排仍然可以独立部署；需要一起考虑的是它们各自学什么，以及各阶段的取舍最终怎样影响用户看到的列表。

**在线架构**层面，仍有系统在细化服务边界。例如某一路召回的资源需求变化较大，可以独立部署和扩容，由召回编排负责调度、融合和降级。也可以在召回和精排之间加入较轻量的粗排，先缩小候选集；粗排是否独立部署，则是另一个问题。当线上模型变多，注册、版本管理和发布流程也可以交给模型平台，预测服务继续负责在线推理。Meta 工程博客的《Journey to 1000 models: Scaling Instagram’s recommendation system》介绍了模型注册、容量评估和发布治理的实践。

从系统整体来看，有几种可以并存的做法：

- **增强多阶段流水线。** 保留召回、粗排、精排、重排等分工，分别提升各阶段的模型能力，也可以让阶段之间共享表示或训练信号。
- **跨场景或跨任务复用模型能力。** 共享模型可以为多个场景提供表示或预测能力，各阶段仍可按候选规模、延迟预算和目标组织计算。
- **在部分环节采用生成式推荐。** 模型可以根据行为历史生成物品标识并映射到实际内容，作为一路召回接进原有系统；也有方案尝试直接生成推荐列表，把部分召回和排序过程合在一起。生成物品标识本身并不等于合并召回和排序，系统上线后仍要处理内容可用性、业务约束和推理成本。用 LLM 生成标签或画像则是另一种用法，改变的是特征生产。

## 9. 总结

回顾这十几年的演进，一方面是回顾这段历史，另一方面也一起探讨演进背后的规律。

首先，演进同时包含替换、叠加、拆分与合并，判断依据是当前的问题和约束。系统演进的这几个动作，在真实系统里，有可能是同时发生的。例如模型在替换、召回源在增加，服务在拆分等等。系统怎么演进，往哪个方向变更，取决于当前最需要解决什么问题。一般会考虑当前的推荐模型效果是不是不够、还是容量撑不住、又或是迭代太慢等等。架构没有先不先进的说法，而是要看能否满足当下的各方面要求。

其次，模型变化往往会把新的压力传到工程链路。比如 GBDT 上线后，推理开销和流量一起增长，推动了 Prediction Server 的独立；增加向量召回后，内容向量的生产、分发与索引更新成了新的配套工作。后续如果引入更长的行为序列，又要重新权衡序列存储和在线计算成本。哪些能力值得单独建设，还是要看具体瓶颈。

第三，从“做出来”到“能规模化做出来”。一般系统的早期，都是考虑某个功能能不能实现，随之上线后的问题是能不能稳定、能不能快速灰度迭代。实验体系、可观测、容灾、特征一致性治理等横向能力，是为了解决这些规模化问题产生的。功能从 0 到 1 有时候比较简单，但要规模化做出来成为一个系统，可能需要花费更多的时间和精力。
